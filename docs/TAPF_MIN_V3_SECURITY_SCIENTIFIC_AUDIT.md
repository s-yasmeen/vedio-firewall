# TAPF-MIN v3 security and scientific audit

Status: pre-federation blocker audit

This document is intentionally conservative. A passed unit test or completed workflow is not treated as evidence that the system is private, accurate, clinically valid, or deployable.

## Current development result

The bounded 24-actor / 144-clip CREMA-D DFA engineering run completed successfully, but the result is a BLOCK-level diagnostic:

- local FER accuracy: 0.1597
- local FER macro-F1: 0.1505
- actor-disjoint folds: yes
- non-private posterior worst measured identity effective AUC: ~0.998
- repeated-release identity effective AUC: 1.0

The local FER accuracy is approximately the six-class chance level (1/6 = 0.1667). Therefore no private-release utility result from this run should be presented as a competitive FER result.

The identity attack on the current out-of-fold posterior is also methodologically confounded because different held-out actor folds are transformed by different FER model instances. An attacker can exploit model/fold fingerprints in addition to any actor information. The result is a warning, not a clean estimate of biometric leakage.

## Release blockers

### B0. FER utility is not adequate

Current deep FER is effectively at chance. Before any system-level claim:

1. run an FER-only baseline with the identity adversary disabled;
2. use a substantially larger actor cohort;
3. add face detection/alignment or a documented equivalent crop;
4. increase temporal coverage and train to convergence with validation-based early stopping;
5. report actor-disjoint accuracy, macro-F1, per-class recall, confusion matrix, and actor-cluster confidence intervals;
6. freeze hyperparameters before final evaluation.

### B1. Current posterior identity audit is confounded

For a clean privacy audit, all privacy-audit actors must be processed by the same frozen FER model, and none of those actors may appear in FER training. Identity attacker training and testing may then use disjoint clips from the same held-out identities.

Required protocol:

- FER development actors: used to train/select the task model.
- privacy-audit actors: never used to fit the FER model.
- one frozen FER checkpoint: transforms every privacy-audit clip.
- identity attacker: trained/tested only on releases from those held-out privacy-audit actors.
- repeated-release attack: aggregates disjoint releases generated by that same checkpoint.

The old cross-fold posterior attack remains a diagnostic stress test but must not be used as the primary leakage estimate.

### B2. Confidence intervals are not actor-clustered

CREMA-D supplies multiple clips per actor. Treating clips as independent in the FER bootstrap understates uncertainty. Final task-utility confidence intervals must resample actors as clusters (all clips for a sampled actor move together) or use another explicitly justified hierarchical procedure.

Identity-attack uncertainty must preserve identity structure; naive clip bootstrap is not sufficient for the final claim.

### B3. Privacy budget is currently resettable

`MinimumDisclosurePrivacyKernel` currently owns an in-memory `BasicDPAccountant`. A process restart therefore resets composition state. This invalidates a deployment-level repeated-release budget unless state is persisted outside the process.

Required production property:

- privacy spend keyed to a declared privacy unit/scope;
- atomic check-and-spend transaction;
- restart persistence;
- concurrency safety;
- replay/idempotency protection;
- audit trail.

### B4. Privacy unit and adjacency require system-level definition

Per-mechanism statements are mathematically scoped, but the research protocol must define the privacy unit that the whole system intends to protect: e.g. one patient encounter, one video, one session, or one person across a time window.

Composition is meaningful only when mechanisms use a compatible privacy unit and adjacency definition.

### B5. Release evidence cannot be trusted if supplied by the requester

A requester must not be able to invent `utility_lower`, `empirical_identity_risk_upper`, epsilon, delta, evaluator IDs, or prior release counts and thereby authorize its own release.

Production release evidence must come from a frozen, versioned, authenticated evidence registry/policy bundle controlled by the deployment authority. Request payloads may identify a policy version but must not define the evidence that authorizes release.

### B6. Server-side composition state is mandatory

The existing service schema exposes `prior_release_count` and composition evidence in the request. The source code correctly warns that production callers should derive this from authenticated server-side state, but that guarantee is not enforced by the current API. It is therefore a prototype control, not a deployment control.

### B7. HMAC attestation has a limited trust model

HMAC-SHA256 provides tamper evidence and authenticity only to parties sharing the secret. It does not provide public verifiability, non-repudiation, hardware provenance, or proof that the measured code actually executed.

For stronger deployment assurance, use asymmetric signatures with key rotation and, if required, hardware-backed remote attestation/TEE evidence. Keep the HMAC mode as a local/prototype integrity mechanism.

### B8. Formal DP and biometric attack resistance remain separate

The DP mechanism bounds changes in the released randomized object under its adjacency definition. It does not imply:

- anonymity;
- no identity inference from side channels;
- no training-set leakage;
- no model inversion outside the release object;
- clinical safety.

Every paper/result must report formal privacy, empirical biometric leakage, and minimum-disclosure size as separate axes.

### B9. Randomness is research-grade, not hardened deployment randomness

NumPy RNG is appropriate for reproducible experiments but should not be the sole security assumption for an adversarial production privacy boundary. Production mechanism randomness requires a documented entropy and state-compromise model and should be sourced through a hardened cryptographic RNG path where practical.

### B10. Side channels are outside the current release theorem

Payload type, request timing, release/block timing, error behavior, session identifiers, logs, caches, crash dumps, telemetry, and network metadata can leak information even when the task payload is DP.

A deployment threat model must explicitly enumerate these channels and either normalize, encrypt, minimize, or exclude them from the claim.

### B11. Minimum-disclosure bits are payload bits, not total leakage

For six classes, a categorical label needs `ceil(log2(6)) = 3` task-payload bits. This does not mean the entire network transaction leaks only three bits. Headers, metadata, timing, repeated queries, policy responses, and side channels are separate.

### B12. The Gaussian posterior mechanism is conservative and utility-poor

The generic bounded-vector Gaussian mechanism uses sensitivity `2C`. For normalized probability vectors, tighter domain-specific sensitivity/calibration may be possible. The current implementation is valid as a conservative mechanism under its stated assumptions, but it is not optimized for utility.

A later version should evaluate analytic Gaussian/RDP/PRV accounting while retaining basic sequential composition as a conservative fallback.

### B13. The current dataset is too small and domain-limited

The 24-actor / 144-clip workflow is an engineering smoke/development test, not the final FER benchmark. CREMA-D is acted emotion data and does not establish telemedicine or clinical validity.

Required progression:

1. larger CREMA-D development cohort;
2. frozen CREMA-D final protocol;
3. external FER/behavioral validation (e.g. Aff-Wild2 where licensing permits);
4. communication utility where relevant (e.g. active-speaker task);
5. AU/motion utility where relevant;
6. clinical validation only with a task-specific clinical dataset and protocol.

### B14. Identity adversarial training may be suppressing task features too early

The three-epoch engineering run ramps GRL strength to ~0.76 in epoch 1 and ~0.995 by epoch 3 while the FER head is still untrained. This can destroy useful representation learning.

Required ablation:

A. FER only, no identity adversary;
B. delayed GRL after FER warm-up;
C. lower adversarial weight;
D. motion-aware branch + delayed GRL;
E. full selected model.

Do not assume adversarial identity loss improves privacy until independent attack results confirm it.

### B15. Face localization/alignment is missing from the deep FER path

The current video reader resizes the full frame. This allows background, framing, illumination, and actor/session artifacts to influence the representation and wastes capacity that should model facial dynamics.

The next FER pipeline should compare at least:

- full frame baseline;
- detected/aligned face crop;
- face crop + motion residual stream.

### B16. Privacy attacks are not yet broad enough

Closed-set identity classification is only one attacker family. Strong final evaluation should add, as relevant:

- verification/linkage attack;
- open-set identity/linkability evaluation;
- repeated-release aggregation across more than two groups;
- attribute inference;
- reconstruction/inversion attempt on released posterior/latent candidates;
- membership inference for trained models (training privacy, separate from current-patient inference privacy);
- attacker transfer across architectures/seeds.

## Gate before federated learning

Federated learning should not be added until the following are true:

- [ ] FER-only actor-disjoint baseline materially exceeds chance.
- [ ] privacy-audit protocol uses one frozen FER model for all audit identities.
- [ ] cluster/hierarchical uncertainty is implemented.
- [ ] release evidence is frozen/versioned rather than requester-authored.
- [ ] privacy unit and adjacency are written down.
- [ ] persistent atomic composition ledger exists.
- [ ] v3 formal privacy kernel is integrated into the service boundary.
- [ ] release/block attestation binds policy version, model hash, evidence hash, mechanism parameters, privacy-scope ID, and cumulative spend.
- [ ] no raw video or task latent is serialized by the release API.
- [ ] side-channel scope is documented.

Only after these gates should federation be introduced as a **training-data locality layer**, followed by secure aggregation and training-level DP. Federation must not be presented as a substitute for inference/release privacy.

## Next engineering sequence

1. Build clean fixed-model FER/privacy audit protocol.
2. Establish a strong FER-only baseline on a larger CREMA-D cohort.
3. Add actor-cluster uncertainty and negative controls.
4. Add delayed/ablation-tested identity adversary and motion-aware branch.
5. Add persistent privacy ledger and immutable policy/evidence registry.
6. Integrate formal privacy kernel with the service and attestation.
7. Run attacks on the exact released objects at each epsilon/disclosure level.
8. Freeze final protocol.
9. Then add federated training + secure aggregation + training DP as a separate layer.
